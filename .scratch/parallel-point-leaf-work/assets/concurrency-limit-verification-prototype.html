Throwaway planning prototype

Choose one point-leaf limit, then prove its contracts

This demo tests the proposal to give point-key routing, point validation, normal lock acquisition, and committed write-back the same initial internal limit. It also maps the deterministic tests and measurements that must reject a bad implementation.

This is a model, not benchmark evidence. Its wave counts follow the bounded execution contract. The implementation must supply the measured latency and throughput data.

Proposed decision

Use one common initial value

  • Sixteen is the smallest candidate that adds at most one backend-wait wave for transactions of up to 32 independent leaves.
  • A transaction does not pay for unused positions. With eight leaves, limits 8 and 16 poll the same eight futures and issue the same backend operations.
  • Thirty-two leaves use two waves. Limit 32 removes the last added wave, but it doubles the maximum per-transaction burst.
  • Keep 16 only if its measured throughput is within 5% of the best candidate. No result yet justifies separate read and write limits.

The sorted serial lock fallback does not use this limit. A future that waits for a foreign holder stays incomplete and consumes one of the sixteen positions. Each transaction gets its own phase bound; there is no database-wide semaphore.

    Measurement plan

    Build each exact leaf count with one pre-created key in each of 1, 2, 8, or 32 collections. Each collection root is one distinct physical leaf. This avoids split timing and gives stable paths. Disable inline publication so the write workloads use the regular logged protocol.

    Selection rule

    1. Sweep limits 8, 16, and 32 through a benchmark-only internal setting. Do not add a public Database option.
    2. For cold single-transaction latency, require at most two waves through 32 leaves. Limit 16 is the smallest candidate that meets this modeled latency budget.
    3. Use the existing worker sweep to find the throughput plateau. Include one and multiple Database clients because the limit is per transaction, not global.
    4. Choose the smallest candidate whose median throughput is within 5% of the best candidate in every converged primary cell. This avoids a larger burst after throughput has stopped improving.
    5. If limit 32 gives more than 5% additional throughput, or the accepted workload requires its one-wave 32-leaf latency, use 32. If one phase saturates earlier, give that phase a measured lower limit instead of adding public configuration.

    • Measure foreground latency and a fixed transaction batch followed by graceful shutdown, so committed write-back debt stays in the throughput result.
    • Compare the common-sixteen implementation with the fixed parent revision in alternating paired order. Use at least three pairs per cell.
    • Record p50 and p95 latency, transactions per second, backend reads and writes per transaction, retries, and lock calls.
    • Record maximum active backend operations. A per-transaction limit cannot by itself enforce a process-wide or provider-wide throughput limit.
    • Keep the existing direct-commit benchmark groups as one-leaf regression gates. The new regular-protocol fixture must not hide a direct-commit regression.
