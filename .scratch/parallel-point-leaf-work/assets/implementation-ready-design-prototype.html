Throwaway planning prototype

Make independent point-leaf work parallel without changing the transaction protocol

This explorer asks whether the nine resolved decisions now form one implementation-ready design. It makes the Rust interfaces, ownership seams, change order, difficult transitions, tests, measurements, and documentation work concrete. It does not implement the design.

Limit 16 is the reviewed initial value, not measured evidence. The implementation starts at 16 and the benchmark compares 8, 16, and 32. Retain 16 only if it reaches at least 95% of the best stable throughput in every primary cell, meets the accepted latency objectives, and passes the parent-regression gates.
The limit bounds one transaction phase, not aggregate backend capacity. Five hundred 32-leaf transactions can admit as many as 8,000 incomplete leaf futures at limit 16. This count is not a request or connection count. GlassDB adds no shared limit, shared backend handle, or global fairness rule. Backend behavior and the provider own aggregate queueing, connection use, retries, and throttling.

The complete shape

One generic seam join_all_bounded

Foreground polling, stable outputs, every input, and no task per leaf.

Domain combination Route or mutate once per leaf

TreeRouter, NodeStore, KeyResolver, and KeyLocker select the unit.

One shared fact AccessSet

Direct and logged commit paths share logical access facts, not physical routing.

One commit point The transaction object

Cross-leaf work stays ordered around the existing logged commit point.

Backend ownership Aggregate capacity stays behind the backend seam

The point-leaf design bounds submissions from one transaction. It does not schedule all transactions.

Code-level decisions that complete the map

These recommendations fill gaps that the behavior tickets did not express as exact Rust seams.

Accepted

Use one private limit bundle

Add a crate-private PointLeafLimits in glassdb-trans. It has one field for each measured phase, with every field initially set to 16. Storage interfaces accept a NonZeroUsize; they do not own product policy.

  • No DatabaseBuilder setting, database-wide semaphore, process-wide semaphore, or shared backend handle.
  • A non-default bench-internals feature exposes one hidden benchmark opening function, not a builder setter.
  • PointLeafLimits::all(n) supports the first sweep; separate fields permit a measured lower value for one phase.
  • The value is an absolute submission bound. It is not a guaranteed percentage of backend capacity.
  • An eight-leaf phase creates eight futures. The unused positions reserve no work or backend capacity.
  • The five fields share a common numeric default, not runtime admission state.
Accepted

Make the routed group contain no duplicate path

RoutedLeafGroup<T> contains one LeafObservation and ordered raw keys with payloads. Its path() comes from the observation. It has no currentness flag and no durable ownership meaning.

  • Groups return in physical path order.
  • Keys remain in original input order inside a group.
  • Each internal item keeps an ordinal until routing finishes.
Accepted

Close the performance acceptance rule

Treat 8-leaf and 32-leaf workload combinations as the primary limit-selection cells. Keep 1-leaf and 2-leaf cells as operation and shape regressions. No repository-wide absolute transaction-latency objective exists today.

  • Use the reviewed one-wave-through-16-leaves and two-waves-through-32-leaves objective for limit 16.
  • Run the real 500-by-32 stress case at limit 16 and against the parent first. Use 8 and 32 as diagnostic cells if 16 fails.
  • Reject crashes, resource exhaustion, sustained provider-error instability, or unbounded benchmark memory. Report absolute stress p95 and p99 until a deployment objective exists.
Accepted

Temporarily instrument a missing stress metric when safe

If a required metric is not exposed, a throwaway benchmark branch can add an accurate measurement hook. Use the result only after at least three converged, alternating paired runs show no measurable change in throughput, p95, or p99, and a deterministic check shows that the hook adds no backend operation. Remove the hook from the implementation branch after the measurement and retain its source commit with the raw results.

  • Prefer existing transport or provider observations when they measure the same quantity.
  • Use the existing two-percent benchmark comparison band as the proposed maximum measurable instrumentation effect.
  • If an accurate, non-perturbing hook is not possible, record the field as notExposed. Never derive it from a different counter.
Accepted

Always use logical validation for locked point reads

A completed acquisition already proves that every required point hold exists. Its leaf load or successful CAS also supplies cache evidence at the shared validation lower bound. Locked point validation can therefore route and read with that bound, then compare the logical point state without branching on how the hold was acquired. The normal read is a local cache hit; eviction or topology churn can require a backend check.

  • Keep batched physical observation checks for optimistic validation before locks are held.
  • Do not use Installed versus Observed to select the locked point-validation path.
  • Keep the existing exact-state shortcut for range coverage, where the alternative is a complete range re-scan.
  • Retain the one-leaf gate that proves this change adds no backend operation with a warm cache.
Accepted

Return a typed serial-renewal action to AttemptDriver

Algo reports that the parallel acquisition episode must end. AttemptDriver then makes the old identity Wounded, renews it, arms a new retirement guard, and calls commit again in forced serial mode.

  • A hard timeout leaves its owner operation unresolved.
  • The new identity samples a new validation lower bound and reacquires collection-directory locks.
  • Point and range work retains the transaction body outcome; collection create/drop repeats the body.
Accepted

Keep best-effort local hold observations

The current KeyLocker::tlocks map records a leaf only after this process receives AcquireOutcome::Locked. Database::diagnostics() exposes those paths and aggregate lock strengths to operators investigating hangs. It is not a durable transaction record.

  • Absence does not prove that no physical lock exists: a CAS can land after cancellation or result loss.
  • Presence is the last confirmed local observation and can become stale after recovery or another process acts.
  • Remove held_paths and aggregate release_locks. Never use the map to skip work, build a hold receipt, drive release, retry, or enter serial mode.
  • If retained, rename the private field, keep the public diagnostics shape plus snapshot and lifecycle-clear operations, and document its per-acquire maintenance cost.
  • The durable recovery manifest written by Monitor::record_tx_locks is separate protocol state and remains unchanged.

Final internal interfaces

Bounded foreground join

pub async fn join_all_bounded<I>(
    futures: I,
    limit: NonZeroUsize,
) -> Vec<<I::Item as Future>::Output>
where
    I: IntoIterator,
    I::Item: Future;

Zero and one inputs use direct paths. The future is conditionally Send; the interface does not require spawning.

Both methods use direct descent for zero or one item. Two or more items use the path-aware ready set owned by TreeRouter. Existing garbage-collection call sites pass one, so this effort does not parallelize garbage collection.

Physical point validation

pub async fn check_leaves_current(
    &self,
    observations: &[LeafObservation],
    validation_start: SequencePoint,
    limit: NonZeroUsize,
) -> Vec<Result<LeafObservationCheck, StorageError>>;

Outputs align with inputs. Exact equal states can share one check. Different revisions and independent absences cannot.

Logical point validation

pub(crate) async fn effective_point_states(
    &self,
    keys: &[KeyRef],
    own_lock_holder: Option<&TxId>,
    validation_start: SequencePoint,
    limit: NonZeroUsize,
) -> Result<Vec<PointValidationState>, StorageError>;

The vector aligns with normalized point reads. Optimistic validation passes no holder. Locked validation passes its transaction identity after LockedTx has proved complete receipts, so an own exclusive hold is not resolved as a foreign writer. One leaf resolves its keys serially; different leaves can wait in parallel.

Leaf hold receipt

enum LeafHoldReceipt {
    Installed {
        cas_precondition: LeafObservation,
        held: HeldLeaf,
    },
    Observed {
        loaded_observation: LeafObservation,
        held: HeldLeaf,
    },
}

Both variants prove a complete hold and provide a freshness anchor for write-back. The skip-capable acquire loads with Requirement::AtLeast(validation_start); a successful CAS advances its precondition evidence past the same bound. Locked point validation therefore treats both variants alike and checks logical point state at that bound. Only an Installed CAS precondition can retain the existing exact-state shortcut for unchanged range coverage; Observed range coverage uses logical scan validation.

Coordinator observation receipt

pub(crate) struct CoordinatedOutcome {
    pub(crate) outcome: FoldOutcome,
    pub(crate) cas_precondition: Option<LeafObservation>,
    pub(crate) loaded_observation: Option<LeafObservation>,
}

A landed staged member has a CAS precondition. A skipped complete same-identity hold has its loaded observation. Reroute, exhaustion, and shutdown have neither.

Capacity ownership stays at existing seams

The final limit review rejects a new GlassDB aggregate scheduler. The implementation adds no production interface between transaction phases and backend capacity.

GlassDB does not learn the backend's active capacity C or schedule aggregate work. Current backend adapters are not guaranteed to have a hard local active-call limit. An isolated 32-leaf phase with equal waits has four transaction-local waves at limit 8, two at 16, and one at 32.

Incomplete leaf futures in one bounded phase glassdb-trans Use the private phase limit. A wait remains incomplete and consumes one position.
Active calls and queues across transactions and Database instances Backend implementation Backend behavior determines which calls are active or queued. This decision adds no hard local cap, common handle, or fairness rule.
Provider requests, streams, connections, retries, and throttling Backend transport and provider Do not derive these values from the leaf-future count. Observe them in stress runs.
Cross-process provider load, file descriptors, memory, CPU, network, and deployment limits Deployment The 500-by-32 long-duration case verifies resource behavior; it does not select a GlassDB aggregate limit.

Use the validated per-transaction phase capacity prototype to explore the 8, 16, 32, and 500-transaction capacity cases.

The backend concurrency capacity research remains factual input. Its recommendation to add a shared GlassDB limit was rejected by the final issue-09 review. Do not implement that recommendation.

Implementation order

1

Build the generic primitive

Add join_all_bounded and prove its direct paths, bound, stable order, all-input behavior, and drop behavior before domain code depends on it.

2

Make routing produce the canonical temporary value

Add RoutedLeafGroup and path-batched descent. Move direct commit to TreeRouter. Remove route_one_leaf only after all callers move.

3

Make validation input-aligned

Add physical and logical batch interfaces. Integrate one shared lower bound while range validation stays in its current order.

4

Add retained-lock receipts

Teach the coordinator and AcquireOperation to produce Installed or Observed receipts. Locked point validation treats both alike; exact range-coverage lookup uses the receipt by path.

5

Change retry and renewal as one safety unit

Add bounded normal acquisition, full-set retry, durable Wounded retirement, and forced serial renewal. Only then remove foreground release as control state.

6

Bound committed write-back

Bound original LockedTx groups. Keep split descendants serial inside their original position and flatten hints only after all positions finish.

7

Verify, calibrate, and record

Add deterministic regressions, run the 8/16/32 benchmark sweep and the 500-by-32 backend stress case against the parent revision, write the new ADR, update only status/link lines in older ADRs, and run make test-all.

Performance matrix

  • Exact 1, 2, 8, and 32 distinct-leaf fixtures: one pre-created key in each of that many collections.
  • Warm decoded cache and cache capacity zero; memory, simulated GCS, and simulated S3 backends.
  • Add explicit none, gcs, and s3 delay profiles so bare memory is a real cell and reports do not hide the selected profile. Keep provider throttling for GCS and S3.
  • Point reads, logged blind overwrites with InlinePolicy::none(), and logged point read-modify-write transactions.
  • One and multiple Database instances, the existing worker sweep, at least three converged paired runs, and cross-run medians.
  • The primary selection cells are the 8-leaf and 32-leaf combinations of all three workloads, both cache states, all three delay profiles, and the converged one- and multiple-Database plateaus.
  • Record p50, p95, p99, transactions per second, reads and writes per transaction, retries, lock calls, maximum active backend operations, and shutdown debt.
  • Treat peak backend work as a whole-workload measure. Caller-joined public reads can make it larger than 16; deterministic unit gates prove each internal phase limit.
  • Run 500 concurrent 32-leaf transactions as separate cold-burst and long-duration cases on real S3 and GCS. Start with limit 16 and a paired parent run. At limit 16, the first admission can contain 8,000 incomplete leaf futures.
  • For the stress case, also record p99 latency, the backend queue, provider requests, connections, retries, provider errors, CPU, memory, file descriptors, network use, and any deployment limit that is on the path.
  • Use a bounded percentile accumulator for the long-duration case. Do not keep every transaction latency sample in memory.
  • Construct an explicit fresh transport client for a cold-pool cell. Reuse one cell client for its warm steady-state run and all of that cell's Database instances.
  • Every optional stress field records its source and availability. For an unavailable metric, first try an accurate temporary hook and prove its effect stays inside the accepted benchmark-noise band. Otherwise record notExposed. Do not calculate queue depth from active-call or leaf-future counts.
  • Use S3 transport interception and fake-S3 connection counters where available. Use CloudWatch, Cloud Monitoring, and process or deployment sampling for provider and host data, with the measurement interval stored in the result.
  • Use the stress results to validate the backend and deployment. Do not derive a shared GlassDB limit or a capacity percentage from them.
  • Keep the existing direct-commit benchmark groups as one-leaf regression gates.
  • Retain 16 only if every one-leaf operation sequence matches the parent, 16 reaches at least 95% of the best stable 8/16/32 throughput in every primary cell, it meets the accepted latency objectives, and no repeatable parent regression exceeds 5%.
  • Use 32 if it gives more than 5% additional stable throughput or an accepted workload requires one transaction-local wave through 32 leaves.
  • If one phase reaches backend saturation earlier, give only that phase a measured lower internal limit.
