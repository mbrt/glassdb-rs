Point-key routing prototype

A throwaway model of four ways to route a transaction's point keys through one cached B-link tree.

Question: Which bounded routing design keeps backend reads parallel across distinct paths, avoids repeated reads of the same node, preserves stable leaf groups, follows stale right links, and adds no backend work for one key?

Working verdict

Prefer path-batched wave descent. It spends the bound on distinct node paths, so clustered keys cannot occupy every slot while other branches wait. It reads the same physical nodes as concurrent independent descent in the normal cold-cache cases, but it completes them in fewer backend waves. It also preserves one load and one observation per routed path.

Keep the current independent descent for the direct one-key path, and keep the existing serial fallback serial. Reject a leaf-chain sweep for sparse point keys: it makes each right link depend on the prior leaf and can read leaves that own no requested key.
