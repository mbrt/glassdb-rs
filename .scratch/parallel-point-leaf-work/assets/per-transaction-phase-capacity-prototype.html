Revised planning prototype

Bound one transaction phase; let the backend own aggregate capacity

GlassDB needs one local answer: how many incomplete leaf futures can one phase of one transaction have? The backend owns aggregate queueing, transport connections, retries, and provider throttling across transactions and Database instances.

A fixed phase limit is not a capacity percentage. Limit 16 is 25% of a backend that can run 64 calls, 3.1% of one that can run 512, and all of one that can run only 8. GlassDB cannot promise a stable percentage without learning the backend's current capacity and scheduling policy.
Ownership is not proof of an existing hard cap. This direction assigns aggregate overload handling to the backend and deployment. It does not claim that every current backend adapter has a local active-call limit. The 500-transaction stress case must observe the actual queue, request, and connection behavior.

Revised proposal

Keep one common transaction-local value

  • An eight-leaf phase creates eight futures. A limit of 16 does not reserve memory, create work, or start another eight.
  • A 32-leaf phase uses two backend-wait waves at 16, four at 8, and one at 32. Thus, 16 is the middle latency-versus-burst choice.
  • Apply the value independently to routing, physical validation, logical validation, normal lock acquisition, and committed write-back as already specified.
  • Do not add a shared GlassDB limit, a BackendHandle, process-wide admission, or transaction-aware global fairness.
  • The backend decides how many submitted calls become provider requests or connections. Provider pressure and cross-process capacity remain backend and deployment concerns.

    ConcernOwnerReason
    Incomplete leaf futures in one transaction phaseGlassDB transaction protocolThis directly controls one transaction's latency waves and local burst.
    Calls active across transactionsBackend implementationOnly the backend knows its client, pool, retry, and provider behavior.

    Selection and verification

    • Sweep phase limits 8, 16, and 32 with exact 1, 2, 8, and 32-leaf fixtures, warm and cold caches, and the specified read, overwrite, and read-modify-write workloads.
    • Keep 16 when it reaches at least 95% of the best stable throughput in every primary cell and meets the accepted p95 and p99 transaction-latency objectives.
    • Use 8 only if 16 gives no material latency or throughput benefit and the smaller per-transaction submission burst has measured value.
    • Use 32 only if it gives more than 5% stable throughput or an accepted workload requires one backend-wait wave through 32 leaves.
    • Use deterministic gates to prove no phase has more than N incomplete futures, all inputs run, outputs stay in input order, waits occupy their positions, and cancellation drops admitted and stored futures.
    • Keep the one-leaf backend operation sequence and count unchanged. A repeatable throughput regression greater than 5% rejects the design.
    • Run 500 concurrent 32-leaf transactions as a backend and deployment stress case. It does not select or create a GlassDB aggregate limit.
